# Phase 1.1: Code Review Report

**Reviewed:** 2026-06-01
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues-found

## Summary

Adversarial review of the route-aware free toll estimator. The change is well-contained
and the locked decisions hold up under scrutiny:

- **Never-throw contract (LD-2) is intact.** `parseAutorouteNumbers` and `classifyTolledKm`
  guard every external field (`ref` null/empty/malformed → `[]`; `distanceMeters` missing → `?? 0`)
  and the regex is anchored and linear (no ReDoS). The `MALFORMED_STEPS` unit test exercises
  the missing-`ref`, empty-string, and missing-`distanceMeters` cases and proves no throw.
- **Signature is backward-compatible (LD-2).** `steps?` is an optional trailing 4th param;
  existing TollGuru branch, the 30-day cache, and TollGuru constants are untouched.
- **Response-shape change is additive and safe.** `getDirections` gains a `steps: RouteStep[]`
  field; the only other consumer (`TripsService.calculateMulti`) reads `geometry`/`waypoints`/
  `distance`/`duration` and is unaffected. `steps` flattening uses `?? []` so a route without
  `legs`/`steps` yields `[]` (→ speed-heuristic fallback), never an exception.
- **Regex edge cases pass.** `"A 6"`, `"A6"`, `"A-6"`, and the semicolon European-route form
  `"A 6;E 15"` all classify correctly; `"D 7"`/`"N 104"`/`null`/`"AD 7"` correctly do not match.
- **No secret/dependency/UI/schema crept in.** No new env var, no new package, no migration,
  `isEstimate: true` always on the estimate path, no web change.

No Critical defects found. Two Warnings concern a wasted heavier Mapbox payload on the
multi-energy path and an end-to-end coverage gap; the Info items are accepted-limitation or
minor-clarity notes.

## Warnings

### WR-01: `calculateMulti` pays the `steps=true` payload cost but discards steps and computes no toll

**File:** `backend/src/trips/trips.service.ts:461` (call site) — together with `backend/src/mapbox/mapbox.service.ts:134` (`steps: 'true'` is now global to all `getDirections` callers)
**Issue:** Flipping `steps` to `'true'` is unconditional on the Mapbox request, so **every** `getDirections` consumer now receives the inflated per-step response (research estimates ~1.5–2.5× wire size for a Paris→Lyon route). `calculate()` legitimately threads `directions.steps` into the toll estimator, but `calculateMulti()` calls `getDirections` and never uses `steps` and never computes a toll — so the extra payload is fetched and dropped on that path. This is a (minor) efficiency/clarity regression introduced by this phase, not a correctness bug. Performance is explicitly out of v1 scope, but the dead data flow is a maintainability smell worth flagging: a future reader will assume `calculateMulti` uses steps because the request asks for them.
**Fix:** Either (a) document at the `calculateMulti` call site that steps are intentionally ignored there, or (b) if precise scoping is wanted later, make `steps` request-conditional. Minimal acceptable fix — add a one-line comment:
```ts
// calculateMulti: steps=true payload is fetched (shared getDirections) but not used here —
// multi-energy comparison does not compute tolls (out of scope this phase).
const directions = await this.mapbox.getDirections(dto.origin, dto.destination);
```

### WR-02: No end-to-end coverage of the real route-aware path — `TollService` is fully mocked in e2e

**File:** `backend/test/trips.e2e-spec.ts:190` (`.overrideProvider(TollService).useValue(tollMock)`) and `:71` (`steps: []` in `DIRECTIONS_STUB`)
**Issue:** The e2e suite mocks `TollService` entirely and the Mapbox stub emits `steps: []`. The e2e assertion at `:528` only verifies that `directions.steps` is *passed* as the 4th argument — it never drives the real classifier with a non-empty `steps` array. Combined with the unit `DIRECTIONS_STUB.steps = []` (in `trips.service.spec.ts:37`), there is **no test anywhere** that runs an `A`-ref step list through the real `TollService.classifyTolledKm` via the HTTP layer. The classifier is well unit-tested in isolation (`toll.service.spec.ts`), so this is a coverage gap, not a proven defect, but a wiring mistake between Mapbox `steps` and the estimator (e.g. a field rename, or steps not surviving serialization) would pass every e2e test. Research's own test map (`trips.e2e-spec.ts` row, TOLL-07) called for "MapboxService mock returns `steps`; assert route-aware `tollCost`" with the real `TollService` — that variant was not implemented (only the mocked-toll variant exists).
**Fix:** Add one e2e case that overrides Mapbox to emit autoroute steps and lets the **real** `TollService` run (drop the `TollService` override for that test, or add a dedicated module without it):
```ts
mapboxMock.getDirections.mockResolvedValueOnce({
  ...DIRECTIONS_STUB,
  steps: [{ distanceMeters: 200_000, ref: 'A 6', name: null }],
});
// with real TollService (no key) → tollCost ≈ 18.0, tollIsEstimate: true
```

## Info

### IN-01: `RouteStep.name` is captured throughout but never consulted by the classifier

**File:** `backend/src/mapbox/mapbox.service.ts:30` / `backend/src/toll/toll.service.ts:246`
**Issue:** `name` is flattened into every `RouteStep` and documented as a "repli rarement utile", but `classifyTolledKm` only inspects `ref`. Steps where Mapbox supplies `ref: null` but a name like `"Autoroute A6"` contribute 0 tolled km (under-count). This is an accepted estimate limitation per LD-6/research, but the captured-yet-unused field is mild dead data that invites "why is name here?" confusion.
**Fix:** Keep `name` (it is cheap and future-proof) but add a one-line note in `classifyTolledKm` that name-only autoroute steps are intentionally not matched, or drop `name` if YAGNI is preferred. No behavioral change required.

### IN-02: A step `ref` mixing a free and a paid autoroute counts its full distance as tolled

**File:** `backend/src/toll/toll.service.ts:251`
**Issue:** `isTolled = aNumbers.some((n) => !FREE_AUTOROUTES.has(n))` means `ref: "A 75;A 6"` (free + paid) counts the entire step distance at the tolled rate. This is internally consistent with the "any tolled A-number → count" intent and is rare in practice (a single step seldom carries two A-refs), but it is an asymmetry worth recording: the free-list exclusion only fires when **every** A-number on the step is free.
**Fix:** Acceptable as-is for an estimate. If finer accuracy is wanted later, document the rule explicitly in the `classifyTolledKm` JSDoc ("a step counts if it carries any non-free autoroute number").

### IN-03: `parseAutorouteNumbers` regex tolerates spurious spacing variants

**File:** `backend/src/toll/toll.service.ts:87`
**Issue:** `/^\s*A\s?-?\s?(\d+)/i` matches not only the documented `"A 6"`/`"A6"`/`"A-6"` but also oddities like `"A- 6"` / `"A -6"`. These are harmless (they still extract the right number) and `ref` is Mapbox-generated, not user input, so there is no injection/ReDoS surface. Noted only for completeness — the loose form will never produce a wrong A-number from real Mapbox data.
**Fix:** None required. If strictness is desired, tighten to `/^\s*A\s?-?(\d+)/i` (single optional separator) — but this risks rejecting a legitimate Mapbox spelling, so leaving it permissive is the safer choice.

### IN-04: `cost: 0` is returned with `isEstimate: true` (no-autoroute / free-only routes)

**File:** `backend/src/toll/toll.service.ts:229-231`
**Issue:** When `classifyTolledKm` returns 0, the result is `{ cost: 0, isEstimate: true }`. This matches research Open Question #3's recommendation (an estimate that found no toll) and the web hides the toll line at 0 (D-04), so it is correct by design. Recording it so a future reviewer does not mistake `0 + isEstimate:true` for an inconsistency with the `{ cost: 0, isEstimate: false }` TollGuru `hasTolls === false` branch (`:213`) — the two zeros are deliberately different (real-zero vs estimated-zero).
**Fix:** None — behavior is intentional and documented in research. Optional: a one-line comment contrasting the two zero branches.
